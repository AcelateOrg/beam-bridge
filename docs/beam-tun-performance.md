# beam-tun: диагностика производительности и фиксы

Дата: 2026-09-21 · Ветка: 1.8.0-xray

Отчёт по жалобам: медленное подключение/переключение (10–15 с), периодические
`ERROR [tun] tun: create tcp endpoint: connection was refused` с зависанием на
10–15 с, скачки пинга до 2000–3000 мс, общие подтормаживания. Ниже — что нашли
и что исправлено.

## TL;DR

Критических архитектурных багов в beam-tun не нашлось: dispatcher, батчи и
backpressure спроектированы
правильно. Но нашлось несколько реальных источников фризов и шума — все
исправлены.

## Найдено и исправлено

### 1. Многосекундные стейлы на записи в TUN (причина скачков пинга 2–3 с)

`device_windows.go`: каждая запись пакета в кольцо драйвера ждала места со
своим таймаутом, и ожидание по пачке суммировалось — под нагрузкой `writeMu`
удерживался секундами, читатель застаивался, RTT улетал.

**Фикс:** общий бюджет ожидания на всю пачку: пачка либо помещается в кольцо
целиком за бюджет, либо хвост отбрасывается (TCP перешлёт, UDP сам восстановится).
Это главный фикс против многосекундных фризов и скачков пинга.

### 2. `create tcp endpoint: connection was refused` — не ошибка

`stack.go`: gVisor возвращает `ErrConnectionRefused`, когда хост отзывает
SYN до завершения рукопожатия (браузер отменил запрос, сканер портов, таймаут
приложения). Туннель тут ни при чём, а строка летела в ERROR и crash.log.

**Фикс:** событие понижено из ERROR в warn-канал (`OnWarn` → runner пишет в
лог как Warn без crash.log), плюс счётчик `debugRefusedEndpoints` в
`debug_counters.go` для диагностики реальной частоты. Зависание на 10–15 с у
пользователя — это был таймаут приложения на отозванном SYN, а не поломка
туннеля; с демоутом и фиксом записи (п.1) картина выровнялась.

### 3. Запуск и переключение сервера

Сначала было ускорено на netsh-батчах, затем полностью переведено на нативный
API — см. UPD в конце документа.

### 4. Логи: либо тишина, либо только ошибки

Ядро генерировало конфиг с `loglevel: warning`, а sink в буфер вкладки
пропускал только warning+ — отсюда «логи тухнут».

**Фикс (сквозной):**

- настройка `LogLevel` (`off|error|info|debug`) в `domain/settings`,
  persistence в `settings.json` (дефолт `info` — информативно, без спама);
- `XrayConfigBuilder.WithLogLevel` — `loglevel` ядра следует настройке
  (`off` → `none`, режим разработчика всегда `debug` + файл);
- `coreLogSink` фильтрует по уровню (`severityRank` против `MinRank`), режим
  разработчика пропускает всё;
- `vpn.Manager.SetLogLevel` применяет уровень на лету, без переподключения;
- UI: на вкладке «Логи» селектор по-русски — **Выключены / Только ошибки /
  Основные / Подробные**. «Выключены» полностью глушит приём строк ядра
  (важно: логи реально можно вырубить).

### 5. Мелочи в горячем пути

- `endpoint.go`: уменьшена максимальная пачка записи — ровнее латентность под
  всплесками, меньше время удержания буферов.
- `monitor.go`, `process_windows.go`: по мелочи из разведки — без изменения
  семантики.

## Что проверено

- `go build ./... && go vet ./...` — чисто (beam-bridge, beam-desktop).
- `go test ./...` — зелёное.
- Боевая сборка `scripts/windows/build.bat` — успешно (Beam.exe, BeamRelay.exe,
  установщик), биндинги Wails перегенерированы с новыми методами.

## Что осталось на потом (не критично)

- Счётчики из `debug_counters.go` пока видны только через pprof/диагностику —
  можно вывести на страницу разработчика.
- Виртуализация списков ProTun (фронтенд) — отдельная правка в
  `RuleNode.tsx` (окно рендера + поиск по списку), к beam-tun отношения не
  имеет, но именно она убирала 10-секундную загрузку вкладки маршрутизации.

## UPD: полный уход с netsh на нативный IP Helper API (2026-09-22, вечер)

После жалобы на медленное ОТКЛЮЧЕНИЕ netconfig_windows.go переписан целиком:
конфигурация адаптера (адрес, MTU, DNS, split/bypass-маршруты) идёт напрямую
в iphlpapi.dll — `CreateUnicastIpAddressEntry`, `SetIpInterfaceEntry`,
`CreateIpForwardEntry2`, `SetInterfaceDnsSettings` — без единого процесса
netsh/PowerShell в горячем пути.

Что это дало:
- нет гонки «адаптер ещё не зарегистрирован» и не нужны ретраи-костыли:
  API возвращает точные коды (ERROR_NOT_FOUND / ERROR_OBJECT_ALREADY_EXISTS)
  вместо локализованного текста netsh;
- отключение = удаление bypass-маршрутов с физического интерфейса +
  сброс DNS — миллисекунды. Адрес/MTU/split-маршруты откатывать не нужно:
  адаптер умирает вместе с TUN-сессией и забирает настройки с собой;
- PowerShell на возврат биндинга tcpip6 из stop-пути убран (биндинг
  отключается один раз за процесс, адаптер всё равно удаляется);
- netsh остался ровно в одном месте: разовое системное отключение
  Teredo/6to4/ISATAP (нативного аналога нет) + фолбэк DNS на Windows
  старше 1903, где нет SetInterfaceDnsSettings.
